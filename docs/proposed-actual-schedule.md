# Proposed / Actual schedule

Schedule keeps the previous evening’s intention separate from today’s edits and explicit attendance. No past proposal is reconstructed from a newer calendar.

## Using it

- Open Schedule → Proposed / Actual. Proposed shows the saved baseline; Actual shows current and previously saved occurrences, actual clocks, and unfinished check-ins.
- Save tomorrow’s proposal from the review. It remains editable before 21:00 in the workspace timezone. The hourly background job freezes tomorrow’s proposal from 21:00 onward. The job must be registered in Inngest; an outage does not invent a baseline for a previous evening.
- A non-blocking bottom card appears on Schedule for a currently due event or an active schedule check-in. Overlapping events open a choice in the day review. Dismiss keeps the prompt quiet for that event/action in the mounted view.
- Hold Started or Ended for 360 ms, slide horizontally to the actual time, and release to save. The ruler moves in five-minute steps. Drag down to cancel. A normal tap opens exact time input; the Times form also handles overnight attendance. Keyboard activation uses the same exact-entry alternative.
- Starting another event parks the earlier timer with `awaiting_end`. Its known start is preserved; its end stays null. Passing the planned end never closes it. An unfinished activity produces no saved session minutes, though the currently running timer remains visible as provisional live time.
- Older starts and ends can be filled in later. Finished canonical sessions can be corrected in place; earlier values remain in outcome history. Conflicting actual clock spans return an error and remain unconfirmed until corrected.
- A matching completed study timer can be reused. Untimed or ambiguous evidence is not automatically attached to an event. Skipped means explicitly skipped; Unknown means unconfirmed.

## Time accounting

Confirmed manual attendance generates only clock ranges uncovered by canonical study sessions or earlier confirmed reports. A timer’s full clock span prevents calendar evidence from restoring deliberately reduced work minutes. Projected manual rows use stable IDs and source `schedule_checkin`; editing or undoing attendance reconciles those rows without deleting original timer sessions. Timer completion replaces overlapping reported rows in the same transaction.

Actual time heatmaps no longer assume attendance from planned calendar events. They deduplicate canonical IDs and integrate overlapping recorded claims at no more than one person-minute per clock minute. Existing integer session minutes remain the storage precision; generated fragments shorter than one minute receive no extra minute.

One shared PostgreSQL advisory lock serializes relevant timer, routine, manual session and attendance writes. UUID command retries and outcome revisions protect against duplicate requests and stale updates from another device.

## iPhone and Shortcuts

The in-app gesture works in Safari and the installed Home Screen web app. iOS owns notification presentation. A web notification opens check-in; it never embeds the custom gesture.

The help panel provides a check-in URL for a URL → Open URLs shortcut and a revocable connection for direct saves. Detailed manual setup is served at `/schedule-shortcuts.html`. Shortcuts uses Apple’s list/date prompts and may open the Shortcuts app for input. No signed `.shortcut` installer or iCloud shortcut link is generated by this release. The shortcut must be assembled on the iPhone.

`/api/schedule-shortcuts/context` accepts only a dedicated bearer key and exposes limited schedule context plus unfinished schedule timers. `/start` delegates to the same start service as the app, with a caller UUID and expected active timer. `/end` requires an explicit timestamp and only accepts scheduled timers. Keys are 256-bit random values, hashed at rest, shown once, expire after 90 days, and can be revoked from authenticated check-in help. They are never accepted by the general API or key-management endpoints. Cookies remain required there. Keys and push subscriptions are excluded from portable exports; a native private database backup retains recovery metadata.

Real live Home Screen/Lock Screen widgets remain separate native WidgetKit/App Intents work. Shortcuts offers launcher buttons and direct API actions, not a continuously updating Marina widget.

## Reminders and deployment

Reminders are opt-in. On iPhone, install Marina to the Home Screen before enabling notifications. The page requests permission only from a user action. The server uses VAPID Web Push; Inngest checks for due starts/ends every five minutes with a ten-minute catch-up window. Delivery is best-effort and subject to device notification settings. No notification creates attendance or ends a timer. Invalid subscriptions are removed; other delivery failures appear in reminder status.

Before deploying, verify a current private production database backup and its restore rehearsal, then apply only `M-035-schedule-review.sql` in one transaction. It adds schedule history, reminder and Shortcuts tables and nullable linkage columns; it does not seed or replace existing data. The Vercel build checks these schema prerequisites before replacing the running app. Register the two added Inngest functions after deployment.

Verification: full unit suite, dedicated local PostgreSQL schedule/timer integration tests (including production-app authentication boundaries), TypeScript, production build, serverless entry/preflight, and Chrome mobile component checks. Physical iPhone notification delivery and the user’s manually assembled shortcuts require on-device verification.
