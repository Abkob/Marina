# P03.1 — Work remaining and calendar reservations

Date: 2026-10-03. Scope: P03.1 of the [implementation checklist](../time-management-copilot-implementation-plan-2026-10-03.md). P03.2 hierarchy rollups and P03.3 interval feasibility remain separate checkpoints.

## 1. Problem reproduced

The previous code had several incompatible definitions of remaining work:

1. Context and planning buckets clamped estimate minus logged work to zero. An unfinished 60-minute task with 70 minutes logged disappeared from some planning views.
2. Schedule proposals and previews also subtracted calendar reservations. A reservation could therefore look like completed work.
3. Parent reservations were credited to descendants; one parent booking could cover multiple children at once.
4. Goal analytics treated completed estimates as time spent when actual time was missing, and automatically multiplied outstanding estimates by historical velocity.
5. Shared calendar blocks without explicit per-task allocations could give each linked task the entire block.
6. A reservation later than a task’s effective deadline could reduce the demand being tested before that deadline.

## 2. Research and decisions

### 2.1 Separate estimates, measured work and a revised forecast

[Jira’s estimation guidance](https://support.atlassian.com/jira-software-cloud/docs/estimate-an-issue/) distinguishes original estimates, logged time and remaining estimates. Marina preserves the original estimate and adds an explicit user forecast. Elapsed time is evidence about effort spent, not proof of the amount of work completed.

[TaskJuggler’s `effortleft`](https://taskjuggler.org/tj3/manual/effortleft.html) demonstrates a separate remaining-effort input in an open-source planning system. Marina adopts that separation without adopting TaskJuggler’s entire scheduling engine or treating its completed-work bookings as Marina’s future calendar reservations.

### 2.2 Keep reserved calendar time separate

[Morgen’s task API](https://docs.morgen.so/tasks) represents estimated task duration and scheduled calendar time separately. Marina now exposes original estimate, recorded work, current remaining forecast, eligible reservations and additional calendar demand as distinct fields. A reservation is neither completion nor a progress report.

### 2.3 Read consistent accounting facts and reject stale writes

[PostgreSQL’s isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html) explains statement snapshots and concurrent updates. The accounting loader reads task versions, session aggregates, links and effective-date inputs in one SQL statement. Forecast writes compare work, log and forecast versions atomically. A competing edit receives HTTP 409 instead of overwriting newer facts.

This is a consistent accounting snapshot, not a claim that every legacy scheduler query runs in one cross-query transaction. Broader scenario freshness and application protocols remain in P17.

## 3. Backend contract

### 3.1 Own-task quantities

`shared/workAccounting.ts` owns the arithmetic used in both browser and server code.

| Quantity | Meaning | Unknown behavior |
| --- | --- | --- |
| `estimated_minutes` | Original user estimate | Missing/invalid is not zero work |
| `logged_minutes` | Session total when available; otherwise legacy reported actual time | Never added to the cached actual total |
| `remaining_minutes` | Current explicit forecast, or the labeled estimate-minus-log approximation | Null when exhausted, unestimated, invalid or stale |
| `reserved_minutes` | Eligible future allocations for this exact task | Invalid/stale allocations do not receive credit |
| `unscheduled_minutes` | Remaining work minus eligible reservations, floored at zero | Null when remaining work is unknown |

An explicit remaining forecast of zero is permitted without completing the task. Only an actual completion state means completed. Unknown remainder is distinct from zero demand.

### 3.2 Forecast freshness

Migration M-032 adds work, work-log and forecast revision counters plus forecast values and their basis versions. Database triggers cover writers outside the new endpoint:

- Material changes to task title, description, estimate, parent or goal invalidate earlier work assumptions.
- Reopening a completed task changes the work version, whether completion was stored in the boolean flag or the legacy `done` status.
- Session insertion, correction, reassignment and deletion change the affected work-log versions.
- Changed reported/cached actual time also changes the work-log version.
- Touch timestamps, ordering, and session spelling corrections do not invalidate a forecast.
- Forecast edits do not change the original estimate or complete a task.

The initial policy is deliberately explicit: new or corrected logs require review of an existing user forecast. It does not automatically subtract a corrected historical log from a point-in-time forecast. More advanced progress-based forecasts belong to later planning phases.

### 3.3 Reservation eligibility

An eligible reservation must:

1. Link directly to the task; there is no ancestor-to-child credit inheritance.
2. Belong to an active calendar event and the requested date window.
3. Still have future minutes. Elapsed portions of a running event are excluded.
4. Match the task’s work version.
5. Fall within the effective task dates, including parent, milestone and goal constraints.
6. Fit the event’s allocation budget. Multi-task blocks require explicit, non-overallocated shares.

Joined duplicate rows are deduplicated by event/task identity. Database uniqueness also prevents two stored links for that pair. Reservations that fail scope, version or allocation checks remain calendar occupancy and are surfaced for review.

Existing accepted links are stamped against their current task version on the first migration. Historical versions cannot be reconstructed. Rerunning the migration never refreshes a stale reservation. Editing an allocation explicitly stamps the current work version.

### 3.4 Read and write API

- `GET /api/tasks/:taskId/work-accounting`: own-task accounting, its 35-day calendar window, observation time and comparison versions. An unavailable task returns 404.
- `PATCH /api/tasks/:taskId/work-accounting`: strict integer-minute forecast or null to clear it, with expected versions. Unknown fields and invalid values return 400. Concurrent changes, completion or disappearance return 409.
- Task list/detail reads include authoritative session aggregates so browser utilities need not assume the actual-time cache is always current.

The endpoint stores a human forecast only. It does not create calendar events, modify resources, use an LLM, or apply a plan.

### 3.5 Consumer inventory

| Consumer | P03.1 change |
| --- | --- |
| Planning buckets | Uses shared own-task arithmetic; unfinished overruns stay visible |
| AI context, task hierarchy and goal context | Shared remainder; unknown goal totals remain unknown with known subtotals/coverage |
| SQL/graph retrieval and deterministic task summaries | Shared remainder and current forecast fields |
| Copilot task-details tool | Returns explicit accounting facts |
| Chat proposals, chat calendar plans and alternative drafts | Use the shared database accounting loader |
| Schedule preview | Uses the same loader; returns work remaining separately from new calendar demand |
| Event autofill and task picker | Honors explicit forecasts and unknown overruns |
| Task/goal time displays | Uses recorded work; historical pace no longer silently changes forecasts |
| Schedule explanations | Separates work, reservations and additional demand; allocated time is not labeled completed work |

Hierarchy selection still follows existing consumer rules. Unifying additive versus inclusive parent estimates is P03.2; this checkpoint unifies the arithmetic for each task, not all hierarchical rollups.

## 4. Frontend behavior

The task focus page has a compact four-value panel: Logged, Work remaining, Reserved, Needs calendar time. On phones it becomes two columns. The secondary “Time details” control explains the forecast basis and reservation window.

The forecast field uses whole minutes and an explicit Save action. Errors remain visible and typed values remain in the field. Background refetches do not silently upgrade the comparison versions of an in-progress edit. After a conflict, Refresh lets the user inspect newer facts and deliberately retry. Saving zero does not complete the task. Save, refresh and detail controls support keyboard use and at least 44-pixel touch targets.

Goal finish-date text is explicitly an illustration at four hours per day with no calendar check. Historical velocity remains descriptive. It is not a calibrated confidence estimate or a deadline guarantee.

## 5. Verification matrix

- Exhausted and overrun estimates remain unknown.
- Explicit remaining forecasts, including zero, remain distinct from completion.
- Session totals and cached actual values are not added together.
- Invalid, negative, fractional, non-finite and oversized minute values do not become valid demand.
- Work/log changes make forecasts stale.
- Reservation duplicates, cancellation/deletion, elapsed time, out-of-window dates, stale versions, parent isolation, shared allocations and inherited deadlines are covered.
- 100,000 joined link rows with duplicates produce deterministic totals under reversed input order.

## 6. Boundaries and remaining work

1. P03.2 still owns additive/inclusive hierarchy rollups, cycle handling and deep-tree performance. Own-task forecasts do not settle parent/child overlap.
2. P03.3 still owns interval-union accounting across overlapping events, DST transitions and focus versus waiting time. Overnight reservations are conservatively flagged for review rather than credited across a date cutoff. Distinct overlapping bookings can still overstate reservations; same-link duplicates are fixed here.
3. Forecasts are supplied judgments. Marina does not yet infer reliable effort from resources, personal history or partial completion. Later P05–P10 phases address those inputs and their uncertainty.
4. A foreground timer’s unsaved/running minutes are not automatically progress. Completed session entries are the accounting input.
5. Date inheritance is applied to reservation credit, but a reserved prerequisite is still unfinished. The scheduler must not infer dependency completion from calendar coverage.
6. Existing capped context lists and resource retrieval limitations remain. P03.1 does not claim a complete large-library reasoning system.
7. The loader reads active-task accounting and timeline metadata; the local stress result does not certify arbitrary production-scale hierarchies or all concurrent load patterns.
8. The new editor retains text during errors while mounted; durable unsaved forecast drafts across navigation are not implemented. Saved forecasts are cloud-persistent.
9. No production load test or live model-quality benchmark is part of this arithmetic checkpoint. The copilot’s reasoning quality is a separate evaluation dimension.
10. Keyboard, touch, accessible names and four viewport widths were checked. A manual screen-reader session and the broader landscape/200%-zoom matrix have not been completed in this checkpoint.
11. Legacy display-only duration text is not silently parsed into scheduling demand. The canonical numeric estimate or a current forecast supplies demand; an old task containing only duration text needs that value normalized through its estimate editor. This keeps browser remaining-work displays consistent with server accounting, including estimates above the legacy editor’s input cap.
