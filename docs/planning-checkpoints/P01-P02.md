## 1. What the user can do now

A task or goal has a discreet **Plan** section. Opening it reads current context; **Start planning** explicitly creates the persistent record. Merely opening a task does not create a plan or fetch its planning context.

The user can record the outcome, approach, decisions and open questions; save revisions; recover manual fields from an earlier revision as an unsaved draft; and archive, restore or forget plan content. A conflicting save preserves the local draft and offers the newer saved version for review. Archive does not complete a task. Save does not create calendar bookings.

This is the persistence and contract foundation for the time-management copilot. The existing chat remains usable, but it does not yet automatically read/write this new plan memory, infer a workload from a collection of documents, estimate effort, discuss all alternatives, or generate scenario evaluations. Those integrations belong to later leaves. A new plan starts empty, with no invented model conclusions.

## 2. Research and architectural decisions

### 2.1 A relational head and append-only revisions

The root references one concrete task or goal. Partial unique indexes allow only one plan per root, including archived plans. Revisions have a composite primary key, a concrete predecessor foreign key and a deferred head-pointer foreign key. The application creates the root and revision zero in one transaction. These choices use PostgreSQL's [constraint](https://www.postgresql.org/docs/current/ddl-constraints.html) and [index](https://www.postgresql.org/docs/current/sql-createindex.html) facilities; database constraints remain authoritative when requests race.

### 2.2 Explicit conflicts instead of silent merges

Writes lock the plan row, verify the submitted base version and append one new revision. The same transaction updates the head pointer. A client cannot overwrite a newer acknowledged revision. Reusing a retry key with the same edit returns its original version; changing that payload produces a conflict. PostgreSQL documents the relevant [row-lock behavior](https://www.postgresql.org/docs/current/explicit-locking.html) and [conflict handling](https://www.postgresql.org/docs/current/sql-insert.html).

The design follows the lost-update protection principle described by HTTP [conditional requests](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match). Marina currently carries `base_version` in its JSON body and returns a structured 409; it does not claim to implement the `If-Match` wire protocol.

### 2.3 Consistent reads, bounded projections

Context and historical-revision reads use a read-only repeatable-read transaction. Helper functions accept the existing database client so they do not take another pooled connection while holding one. PostgreSQL's [isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html) explains why several reads under ordinary read-committed isolation can otherwise observe different database states. External Drive access cannot participate in the SQL snapshot; it is separately checked before returning evidence.

Plan writes serialize against other plan writes. They do not lock all task/calendar/source records. If those facts change during or immediately after a save, the next context read reports staleness. P02 does not apply schedules or make calendar-feasibility guarantees; P17 must independently verify its complete read set at Apply.

## 3. Expanded child checklist and acceptance evidence

### P01.2 — Plan, scenario and provider states

#### P01.2-a [x] Separate the meanings of ready and complete

- Plan state: draft, revising, current, stale, archived. A transition map rejects unsupported transitions. `revising` is available to later orchestration; manual editing stays local until Save.
- Scenario state: evaluating, ready, partial, conflicted, failed, canceled, superseded. No scenario state means human work was completed or a calendar change was applied.
- Provider outcome: success, unavailable, canceled, invalid response. Retryability is explicit for unavailable/invalid responses.
- Evidence coverage and schedule feasibility are independent fields. Unconditional feasibility requires complete evidence, successful evaluation and no assumptions. Conditional feasibility requires stated assumptions, which the UI displays.
- Tests: `audits/planning/state.test.ts`, the six persisted outcome cases in `persistence.test.ts`, and `ScenarioStatus` component cases.

#### P01.2-b [x] Make terminal writes authoritative

- An evaluation starts against a signed scope/snapshot, current revision and stable request key. Duplicate starts return one scenario ID; changing the context under that key conflicts.
- Completion locks the plan before the scenario. Only an evaluating scenario can accept a terminal result. New revisions invalidate pending/current scenario artifacts.
- A canceled result cannot be replaced by 100 late successes. A separate 100-event mixed cancellation/failure race produces exactly one accepted writer.
- Snapshot changes supersede results even when the plan's own version did not change. A read also suppresses old results under another scope or changed facts.
- No public endpoint accepts a fabricated evaluation. The repository lifecycle and UI presentation are ready for the later evaluator.

### P01.3 — Scope, versions and errors

#### P01.3-a [x] Keep evidence, calendar context and writes separate

- Evidence belongs to an active task/goal through saved resource relationships. Existing Marina-root Drive ancestry checks still apply. Semantic similarity cannot invent ownership.
- Explicitly selected resources narrow the scope. An empty selected list means no resources. Subtask inclusion is explicit for task roots.
- Busy intervals come from workspace commitments in the selected date window. Their titles are removed from the planning projection; unrelated resource text is never added to justify calendar context.
- The proposed write set contains only this plan. It grants no task-edit or calendar-write authority.
- Work-item task references are checked against the selected active task tree. A resource ID cannot act as a task reference.
- Root-keyed UI instances and response sequence checks prevent an old request from replacing another root's context.

#### P01.3-b [x] Bind cursors and snapshots

- Tokens bind token purpose, canonical root/selected IDs/subtask flag/date window, material-fact digest, revision, expiration and pagination position. HMAC uses a separate planning domain with the existing workspace signing secret.
- Tokens expire after 15 minutes. Production refuses to use a temporary signing secret. Local development can use a process-local key, which deliberately invalidates tokens on restart.
- Material facts cover the selected root/task tree, recursive prerequisite task state, dependency/relationship edges, linked milestones/deadlines, work sessions, resource manifest generations/status, schedule preferences, daily overrides and workspace busy intervals.
- Navigation timestamps and display positions are excluded, preventing merely opening a task from invalidating its plan.
- Display pagination and evidence validation are separate. A work item referencing source 25 remains valid while the UI shows sources 1–20. Missing, unlinked, archived, revoked or generation-mismatched sources are redacted on both current and historical reads.
- Tests replay a real cursor across 50 roots, verify no evidence appears there, exercise revision-invalidated cursors and save later-page evidence. Signature, expiry, purpose and narrowed-scope tests supplement these cases.

#### P01.3-c [x] Return actionable errors without losing drafts

- New endpoints return stable codes including `invalid_payload`, `scope_mismatch`, `snapshot_stale`, `stale_revision`, `idempotency_conflict`, `source_unavailable` and `not_found`.
- Validation runs before expensive retrieval; API responses use `Cache-Control: no-store` and existing workspace authentication.
- Lost save responses preserve the same retry key. Conflicts reload current server state while retaining the user's unsaved fields. A deliberate review action rebases the draft; Save remains a separate action.
- An unavailable source check fails closed. Failed context refreshes remove the old server context from view while keeping the user's local draft.

### P02.1 — Storage and migration

#### P02.1-a [x] Add three bounded tables

`planning_plans` stores root identity, head version and lifecycle. `planning_plan_revisions` stores bounded planning content, origin, operation, predecessor, retry key and fact hash. `planning_scenarios` stores evaluation lifecycle, scope/fact binding and bounded results. None duplicates complete source documents, all task facts or calendar contents.

Migration `031-persistent-plans.sql` is additive and is mirrored in `server/schema.sql`. It creates no demo plans and assigns no inferred attachment roles. Current resource projections label roles `unspecified`.

#### P02.1-b [x] Rehearse upgrade and restore before production

The repeatable script `scripts/rehearse-planning-migration.ts` first verifies a deliberately marked loopback test database. It creates unique test databases instead of restoring over an existing one. It tests:

1. Empty current schema and the prior deployed schema.
2. Repeated application of the migration with a preexisting legacy task preserved.
3. A custom PostgreSQL dump restored into a new database.
4. The application's portable backup, checksum verification and actual restore command into another new database.
5. Recovered plan content and rejection of an invalid head pointer after each restore.

The successful final rehearsal receipt is `tmp/planning-baseline/p02-migration-rehearsal.json`, timestamp **2026-10-03T15:12:49.718Z**. This uses synthetic data; it does not restore production data into a local development application.

#### P02.1-c [x] Verify concurrency and access cost

Twenty simultaneous creates return one root and one revision zero. Ten thousand synthetic roots retain indexed exact-root lookup; duplicate creates preserve the existing root. Context responses paginate resources and report omissions. This verifies relational behavior, not terabyte-scale ingestion or Drive throughput.

### P02.2 — Editing, conflicts and recovery

#### P02.2-a [x] Keep head and revision atomic

Two competing edits have one winner and one explicit conflict. A 100-edit burst yields one new revision and 99 conflicts. An injected database trigger fails the head update after revision insertion; the transaction rolls back both, and a later retry succeeds. An idempotent retry cannot duplicate history.

All revisions record `user`, `assistant` or `system` origin. Current HTTP edits are always `user`; the client cannot supply origin or lifecycle state. Assistant-written content is not connected in this slice.

#### P02.2-b [x] Preserve a usable draft

The editor preserves manual outcome/approach/decisions/questions locally per typed root. It does not cache derived work-item text. Reload keeps pending edits visibly distinct from the last saved revision. Storage failure displays a warning instead of pretending the draft is protected.

Decisions and questions allow Enter while typing and save as separate lines. Client and server validate their bounds. A lost response keeps the unchanged retry key, which permits a safe repeat Save.

#### P02.2-c [x] Offer explicit historical recovery

History is metadata-only until a revision is selected. Loading an older revision recovers manual fields as a draft and requires Save to create another revision. Source-derived work items remain based on the current validated server revision; they are not revived from the browser or a stale historical cache.

The API pages history in groups of 20; the initial UI displays the newest 20. A full historical explorer is deferred. Archived plans must be restored before editing or recovering content.

### P02.3 — Lifecycle and retention

#### P02.3-a [x] Keep archive separate from completion and deletion

Archive creates a revision and excludes scenario artifacts from active presentation. Restore creates a draft revision. Archiving a goal makes its branch's plans unavailable; restoring that goal exposes the existing plans again. Deleting a source task/goal cascades its dependent plan records, while independent resource originals remain untouched.

#### P02.3-b [x] Make forgetting truthful

Forget is available for archived plans and describes its consequences before confirmation. It clears planning content across all revisions and scenario result bodies, preserving version/origin/operation metadata and retry hashes. Tasks, resource files, existing chat messages and preexisting backups are not erased. Restoring a forgotten plan recovers an empty editable plan, not erased content.

User-entered prose is retained as a user fact. Automatically derived text must carry source provenance in work items to receive source-based redaction. This slice must not be used by future integrations to copy generated source prose into untracked manual fields; P07/P10 must extend provenance before doing so.

#### P02.3-c [x] Bound transient artifact retention

- Evaluating artifacts older than 30 minutes become failed.
- Result bodies older than seven days are cleared and marked superseded.
- Maintenance handles at most 100 eligible rows per run with row locks and skip-locked selection; interrupted/repeated batches do not delete plan history.
- Required revision lineage and scenario metadata remain until root deletion or an explicit future retention policy. There is no automatic pruning of a user's decisions.
- Existing P00 diagnostic traces keep their own seven-day/100-row policy. Google Drive originals have a separate lifecycle.
- Read-time freshness/redaction acts independently of the cleanup schedule. Maintenance failures are reported as a null cleanup result, not a false zero-success count.

## 6. Remaining bounds and limits

1. Plan content remains within P01's 256 KiB/depth/node limits, with 100 work items and at most 100 distinct evidence sources per revision. Outcome: 4,000 characters; approach: 8,000; decisions/questions: at most 30 each, 500 characters each. These are revision/API bounds, not a total library size limit.
2. Resource manifests return 20 items per page; explicit resource selections currently accept 20 IDs. The initial panel shows a count and omissions; it is not the future resource-role picker. Evidence validation separately checks sources referenced by the plan.
3. Context windows are at most 90 days. The initial editor requests seven local-calendar days. At most 200 busy intervals are returned, with an omission count. Future feasibility code must not treat an omitted interval list as a complete schedule.
4. SQL aggregates fingerprints across the relevant metadata. Existing calendar/routine helpers still have broad reads and existing timezone behavior. P03/P12 must unify time semantics, optimize those queries and measure real-library/context latency.
5. Drive checks use current provider access/ancestry checks but remain subject to network latency and permissions changing after a response. A loaded screen is not a continuously revoked remote document session; the next read/refresh revalidates it.
6. Local manual drafts live on that browser only. They are not cloud backups, cross-device drafts or a multi-user identity boundary. Clearing browser storage loses unsaved edits. Source-derived work items are excluded from that cache.
7. The application still uses its existing single-workspace password gate. New root checks enforce that workspace's task/goal boundaries; they do not add tenant-level authorization.
8. Revisions and audit metadata grow over time. Seven-day cleanup applies to transient result bodies, not all revision history. A large production storage benchmark and configurable long-term retention remain future work.
9. Existing `RAG-02`, `VIS-01` and `VIS-02` remain recorded. P02 does not improve model availability, embedding quality or all-page image understanding.
10. The existing frontend bundle is approximately 2.86 MB before compression and emits the known large-chunk warning. This foundation introduces no new model SDK or provider dependency.
