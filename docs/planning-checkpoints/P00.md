## 1. What changed

Previously, baseline tests lived in separate suites, expected failures appeared inside Vitest's green count, and chat response details chiefly showed model timings. Reproducing a planning problem did not supply one reusable fixture/receipt or a bounded phase record connecting a response to its proposal.

P00 adds immutable work/calendar/evidence fixtures, a reproducible baseline command, explicit known-failure accounting, and a separate diagnostic stream. New chat responses can show “Loading context,” “Checking sources,” “Preparing an answer,” “Checking available time,” “Checking proposed changes” and “Saving the conversation” when those operations actually run. A successful durable proposal Apply adds a correlated event visible on history reload. A dropped diagnostic write is labeled independently of the saved chat.

No production schema migration, resource reindex, model change or new dependency is required. Diagnostic rows reuse the existing agent ledger; prompts, tool arguments, source bodies and credentials are excluded from this new stream.

## 4. P00.3 — Diagnostic contract and persistence

Files: [shared contract](../../shared/evaluationTrace.ts), [recorder](../../server/services/evaluationTrace.ts), [storage and retention](../../server/services/evaluationTraceStore.ts), [conversation integration](../../server/services/copilotConversation.ts), [response details](../../src/components/CopilotTraceDetails.tsx).

### 4.1 Runtime boundaries

The real conversation loop records model attempts, actual tool calls and proposal validation. Session routes add context/persistence measurements and correlate the request UUID with the existing `agent_runs` UUID. Durable proposal IDs are attached to the trace; Apply appends an event only after the application transaction commits.

Failure categories distinguish timeout, unavailable provider, empty evidence, invalid response/proposal, denied scope, tool failure and storage failure. An empty search is partial evidence, not a provider timeout. Storage classification uses the operation phase, so an HTTP-like status 500 cannot relabel a database write as a model outage. Unexpected telemetry shapes are dropped without replacing the core result.

### 4.2 Privacy, size and retention

The allowlist contains only phase/status/failure enums, UUIDs, timings, counts, optional source generations and a configuration fingerprint. Extra fields are stripped. Tests include synthetic bearer tokens, headers, private document text and hidden reasoning and verify none appears in serialized diagnostics. This is not a redaction retrofit for existing application logs or chat history.

Each trace permits 48 events, eight source references per event and 30 proposal IDs. Recorder and subsequent Apply additions stay within 24 KiB. Excess events and source references increment omission counters. The UI shows eight phases initially; additional measurements and identifiers are in secondary details.

One `evaluation_trace_v1` snapshot is stored per agent run, independently of chat metadata. History hydrates it separately. Expired/malformed/missing traces do not hide saved messages. The seven-day retention job removes at most 100 expired diagnostic rows per maintenance run. It never removes chat, proposals, sources, runs or other ledger events. Reads hide expired traces even before batch cleanup finishes.

Storage operations use a 750ms statement timeout and catch diagnostic failures. Connection acquisition still uses the existing pool's 5-second timeout; P00 does not promise a 750ms end-to-end deadline. Additional database work can add latency. Missing diagnostics are visible and do not imply that a task or calendar change failed.

## 7. Remaining limits and continuation

- **Identity/retrieval defects:** `CHAT-01` and `RAG-02` remain reproduced. The new diagnostic layer observes behavior; it does not make unsafe identities valid or irrelevant evidence useful.
- **Work accounting:** duplicated estimate-minus-logged/reservation calculations remain inventoried for P03. Unknown effort and unfinished overruns need that phase's shared semantics.
- **Planning capability:** persistent/revisable plans, purpose-aware resource analysis, effort forecasting, hypothetical scenarios and decision memory remain future sections.
- **Coverage boundaries:** P00 correlates session agent runs and durable proposals, not every asynchronous indexing job or legacy calendar Apply. Forecast/UI runtime instrumentation follows the actual features. Pre-run session failures and existing ledger failure coupling remain outside this diagnostic retrofit.
- **Operational limits:** database connection acquisition/queries can add latency; cleanup is batched; browser-local cached operational metadata may remain until cleared even though the UI hides expired traces. No multi-user ownership migration is implied.
- **UI baseline:** preview tests preserve existing behavior; they do not certify every legacy calendar control's mobile design or fix all broader chat-save error messages. P16/P17/P21 retain those responsibilities.
- **Scale/quality:** small reproducible fixtures and bounded telemetry do not establish large-library retrieval quality, model reliability, end-to-end visual coverage or production throughput.

**Decision: continue at P01.1 when requested.** Its fixture prerequisite is satisfied. Define typed planning references first and turn `CHAT-01` into a normal passing regression; retain this baseline and its known-failure accounting while doing so.
