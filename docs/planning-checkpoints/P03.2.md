## 1. Research translated into behavior

### 1.1 Original work, own work and hierarchy totals

[OpenProject’s progress documentation](https://www.openproject.org/docs/user-guide/time-and-costs/progress-tracking/) distinguishes a work package’s work from aggregated hierarchy work. Its [15.5 release notes](https://www.openproject.org/docs/release-notes/15/15-5-0/) describe visible hierarchy totals. Marina adopts separate own/subtree values and an expandable breakdown. This is a comparison with documented product behavior; it is not a claim that OpenProject’s calculation implementation was audited or copied.

[Jira’s time-tracking explanation](https://support.atlassian.com/jira/kb/how-to-bifurcate-time-spent-and-time-remaining-in-time-tracking-field-for-standard-and-subtask-issue-type/) provides a useful additive parent-plus-subtask example. Marina also supports its existing inclusive relation. OpenProject’s treatment of missing estimates is not adopted: an unestimated child must leave Marina’s total partial, not disappear from it.

[PostgreSQL recursive queries](https://www.postgresql.org/docs/current/queries-with.html) inform the database guard and ancestor invalidation. The implementation uses duplicate-eliminating `UNION` for ancestor traversal, plus an application advisory lock before HTTP reparenting updates. The application aggregation is iterative and has no recursive stack dependency.

### 1.2 UI adoption

The task time panel shows a compact **Task + subtasks** remaining total. **Counted work** opens the direct child breakdown and separate parent work. The existing restrained visual language is retained; the toggle has a 44px touch target, keyboard access and visible focus. Child titles wrap, and the numeric values remain readable on a 320px screen. Parent forecasts explicitly ask for work outside the subtasks. Unknown totals say **partial**, and the explanation does not depend on hovering.

## 2. Accounting contract

### 2.1 Where the relation lives

`time_rollup_mode` is stored on the **child** and describes that child’s relationship to its parent. Existing `inclusive` and `additive` values, including mixed children, remain supported. The migration does not rewrite estimates or modes.

For each parent, original aggregate estimate is:

```text
max(parent original estimate, included child subtree estimates)
  + additional child subtree estimates

parent residual estimate = max(0, parent original estimate - included child subtree estimates)
subtree remaining = parent residual remaining + each child's subtree remaining
```

These are known values only when the required inputs are known. A missing included-child estimate makes the residual unknown. An unestimated container with known children does not invent extra parent effort. An explicit parent remaining forecast refers to separate parent work; it is not a replacement for the children’s forecasts.

### 2.2 Worked examples

| Original structure | Parent residual | Subtree remaining before logs |
| --- | ---: | ---: |
| Parent 120, two included children 60 + 60 | 0 | 120 |
| Parent 30, two additional children 60 + 60 | 30 | 150 |
| Parent 150, two included children 60 + 60 | 30 | 150 |
| Parent 240, included child 90, additional child 120 | 150 | 360 |
| Parent 120, included children 60 complete + 60 unfinished | 0 | 60 |
| Parent 120, included child unknown + included child 60 | Unknown | Partial: 60 known |

Completed children retain their original allocation inside the parent budget. Otherwise completing a child would incorrectly recreate parent work. Logging 20 minutes on a child reduces that child’s estimated remainder, not the parent residual. An exhausted unfinished estimate is still unknown, as established in P03.1.

### 2.3 Identity, malformed data and limits

Each task ID owns one work item. Repeated identical joined rows count once. Conflicting duplicate accounting values, missing parents, unloaded children, malformed cycles and invalid modes make affected totals incomplete. A completed parent with an unfinished child is inconsistent even if the child has a zero-minute forecast.

The task API includes direct child counts so a partially loaded list cannot pretend it loaded the whole subtree. The authoritative work endpoint aggregates all visible tasks before returning the requested task. Its expanded card returns at most 20 direct children, plus the full total and omitted-child count. The omitted rows are not excluded from arithmetic.

## 3. Implementation steps and evidence

### P03.2.1 — Shared aggregation

- `shared/workHierarchy.ts` builds a deduplicated forest, resolves ancestor paths iteratively, and aggregates children before parents.
- It returns original/residual estimates, own accounting, subtree remaining and logged work, known subtotals, unknown counts, issues and executable status.
- Unit cases cover inclusive/additive/mixed children, completed included children, explicit residual forecasts, logs, partial loads, conflicting duplicates, self/multi-node cycles, 10,000-deep and 10,000-wide structures.
- A seeded 500-tree test checks order/duplicate invariance and agreement between root totals and the sum of unique residual work items.

### P03.2.2 — Calendar and scheduler use

- The shared snapshot feeds both chat scheduling and the schedule-preview endpoint. Parents with separate work can execute; pure containers do not receive a second allocation.
- Exact event-task ownership remains authoritative. A parent block no longer makes descendants appear reserved in the conversational overview.
- Task selection and calendar autofill use residual work where a complete hierarchy is available.
- A completed task, a zero forecast and a calendar reservation remain distinct states.

### P03.2.3 — Dependencies across a hierarchy

- `shared/hierarchyDependencies.ts` expands a parent prerequisite to its executable descendants and residual work.
- A prerequisite on a parent also applies to its descendants. Repeated edges are deduplicated.
- Missing, invalid or unfinished zero-work prerequisites remain unresolved; completed valid prerequisites can be omitted.
- Expansion stops at 100,000 distinct dependency pairs and returns an unresolved blocker rather than silently dropping dependencies.
- Tests cover expansion, inheritance, completed/unknown prerequisites, cycles and a 10,000-deep chain. Database tests confirm chat receives the expanded prerequisites.

### P03.2.4 — Durable invalidation and concurrency

- M033 updates the work-version function to include rollup-mode changes.
- Inserting, deleting, reparenting or semantically changing a child invalidates affected ancestors. Reparenting invalidates both branches. Timestamp-only edits and child log corrections do not change a parent’s separate-work forecast; the live subtree total still reflects the child’s log.
- Existing parent forecasts/reservations are invalidated once because their former interpretation may differ. No historical session is reassigned or deleted.
- HTTP reparenting takes the hierarchy lock before updating a row. Database checks reject self-cycles, ancestor cycles and attachment inside an existing malformed cycle.
- Real PostgreSQL tests cover concurrent reparenting, forecast invalidation, repeat migration, unchanged session ownership and superseded in-flight planning scenarios.

### P03.2.5 — Frontend and Copilot consumers

- Task estimate/actual/progress utilities, goal analytics, the goal health panel, scheduling selection and the time panel use the shared hierarchy arithmetic.
- Task tree rendering reuses one memoized accounting result rather than rebuilding it for each displayed row.
- Calendar picker traversal is iterative and deduplicated; its indentation and context length are bounded.
- Copilot task details expose separate own and subtree values. Retrieval overwrites current effort fields from the authoritative snapshot and strips stale cached estimate lines.
- Task-domain rules explain residual work and partial totals only when that domain loads. They forbid inventing what parent effort involves from a title.
- Component and browser cases exercise expansion, partial totals, keyboard/touch controls, persisted changes, stale writes and narrow-screen layout.

### P03.2.6 — Migration, backup and restoration

- `scripts/rehearse-work-hierarchy-migration.ts` exercises an empty schema, upgrade from `833c563`, repeated application, a custom PostgreSQL dump restore and a portable restore in fresh, marked local test databases.
- The restored child relationship, forecast/work/log stamps, stale reservation, revision-head foreign key and five enabled accounting/hierarchy triggers are asserted.
- Portable restore disables these application triggers only inside its restoration transaction, then enables them before commit. Restoring history must not be interpreted as newly edited work.
- `scripts/deploy-work-hierarchy-schema.ts` requires a backup under one hour old, matching production database identity and verified local/private-cloud checksums. It requires the exact migration hash to have passed the restore rehearsal, takes a deployment lock, checks legacy row counts and commits only M033.
- The deployment build gate requires M031–M033 and all five triggers. A Git push alone is not treated as a database backup or migration.

## 6. Remaining limitations and next boundary

1. P03.3 still owns interval unions, overlapping reservations, waiting vs focused effort and fuller timezone/DST feasibility. This change does not promise optimal scheduling.
2. The 10,000-task stress tests establish aggregation/dependency traversal, not rendering 10,000 expanded rows or a production database write-latency SLA. Other legacy task-tree/date traversal utilities remain outside that claim.
3. The accounting loader reads the visible task hierarchy and relevant ledgers. It is not yet an incremental materialized aggregate for million-task workspaces. Paginated/goal-filtered frontend lists can show partial totals; the task accounting endpoint is authoritative.
4. Ambiguous parent logs remain owned by the parent. They are not distributed across children automatically. A user may need to revise an explicit residual forecast when historical logging mixed both kinds of work.
5. Explicit task dependencies can expand considerably across hierarchies. The pair cap deliberately makes scheduling unresolved rather than dropping constraints. A future compact dependency representation can improve this bound.
6. A fully reserved but unfinished prerequisite is handled conservatively when absent from new scheduler demand. Existing calendar blocks are not proof of completion; more precise prerequisite completion placement belongs with interval feasibility.
7. Goal health’s simple available-hours heuristic and historical velocity are not calibrated duration prediction or a full calendar feasibility assessment.
8. Persistent plan memory remains manual. Automatic chat use of plan memory, resource effort inference and multimodal evidence quality remain later sections. The correctness of options already produced using current task facts is now a P03.2 repair requirement; it cannot be deferred to future option-generation work.
9. Hosted model availability and semantic accuracy remain material limits and now block P03.2 closure under section 8. Existing green unit totals do not resolve them.
10. Re-indexing documents is unrelated to this migration. No Drive originals, embeddings or document content are rewritten.

### 8.2 Design requirements and boundaries

1. **One factual basis from database to answer.** Use the current shared accounting snapshot, typed entity IDs, explicit own/subtree scope, completeness and versions. A title or old assistant message is not authoritative evidence.
2. **Model-led discussion remains the product.** The model chooses useful questions, investigations and alternatives. Do not replace it with a fixed menu, mandatory four-option template, keyword router or automatic “drop optional reading” policy. Deterministic checks constrain unsupported facts and invalid arithmetic; they do not decide the user's priorities.
3. **Resource roles do not redefine tasks.** An optional reference is not proof that a task is optional, that required reading can be skipped, or that a draft satisfies a deliverable. Read the association/requirements when available; otherwise state a conditional option or ask a useful question. Do not invent missing resource contents.
4. **A valid schema is insufficient.** Structured claims allow exact verification, but free-text advice can still contradict them. Validate typed facts and evaluate the actual prose. Correct metadata alongside a wrong answer is a failure. A second model is supporting review, not an infallible oracle.
5. **Bounded repair, useful degraded behavior.** Allow one proposed semantic correction attempt within the existing overall request budget; validate it again. If it fails, return only an independently rendered, verified fact summary and a concise explanation that advice could not be verified. Do not display the invalid recommendation as accepted or label this fallback a successful planning answer.
6. **Availability, correctness and usefulness are separate.** A provider outage cannot be fixed by a prompt; a correct greeting cannot certify planning. Keep unavailable checks open. A retired/inaccessible model may receive verified unavailable handling, but that is not the same as passing its live-answer tests.
7. **Keep the core prompt small.** Load hierarchy/option rules with the relevant domain or evidence. Do not attach all resources, tool schemas or repair instructions to a greeting. Do not expose hidden reasoning; retain safe stage timings and verdicts instead.

The evaluation design borrows the distinction between programmatic assertions and model-assisted rubrics documented by [Promptfoo](https://www.promptfoo.dev/docs/configuration/expected-outputs/). Marina can implement this with its existing Vitest/live harness; adopting a new dependency is not required. [NVIDIA's RAG troubleshooting](https://docs.nvidia.com/rag/latest/troubleshooting.html) identifies 429 as rate limiting, while its [FAQ](https://forums.developer.nvidia.com/t/nvidia-nim-faq/300317) discusses variable limits and shared endpoint load. These references justify separating error classes; they do not identify the root cause of Marina's 504s or prove a particular model is healthy.
